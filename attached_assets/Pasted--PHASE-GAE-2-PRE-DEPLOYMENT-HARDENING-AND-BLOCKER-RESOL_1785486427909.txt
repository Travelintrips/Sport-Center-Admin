## PHASE 4 — SECRET MANAGER DESIGN

Hapus rencana deployment berikut:

gcloud app deploy ... --set-env-vars="SECRET=..."

Jangan mengirim secret melalui command line.

Siapkan desain penggunaan Google Secret Manager.

Gunakan nama secret yang dipisahkan untuk production, contohnya:

sport-center-prod-supabase-database-url
sport-center-prod-session-secret
sport-center-prod-fonnte-token

Jangan membuat nilai secret dan jangan meminta nilainya.

Audit mekanisme aplikasi saat ini:

- apakah aplikasi sudah memiliki secret loader;
- apakah secret loader hanya bekerja di Replit atau GCP;
- apakah dapat membaca Google Secret Manager memakai Application Default
  Credentials;
- service account runtime apa yang akan dipakai;
- IAM role minimum yang dibutuhkan.

Gunakan:

roles/secretmanager.secretAccessor

hanya pada secret yang diperlukan oleh runtime service account.

Cloud Build harus memakai `availableSecrets` hanya apabila build benar-benar
memerlukan secret. Jangan memberikan production runtime secrets kepada step
build jika build tidak membutuhkannya.

Secret Manager adalah metode yang harus digunakan untuk data sensitif pada
Cloud Build, bukan substitution biasa atau plain environment value.

## PHASE 5 — REPLIT OBJECT STORAGE COMPATIBILITY

Audit seluruh penggunaan:

@replit/object-storage
replitStorage.ts

Cari semua route dan service yang bergantung padanya.

Laporkan:

- fitur yang terdampak;
- apakah dipanggil saat startup;
- apakah kegagalan storage dapat membuat server crash;
- apakah hanya digunakan saat upload/download tertentu;
- data apa yang saat ini disimpan di Replit Object Storage.

Karena production sudah memakai Supabase, prioritaskan Supabase Storage,
bukan membuat storage provider baru tanpa alasan.

Buat storage abstraction yang mendukung:

- Supabase Storage untuk production GAE;
- implementasi lama hanya bila masih diperlukan untuk development;
- tidak ada koneksi ke 127.0.0.1:1106 di production;
- clear error handling;
- tidak ada silent fallback yang menghilangkan file.

Jangan melakukan migrasi file lama tanpa inventaris dan persetujuan.

Tambahkan test untuk memastikan production mode tidak pernah mencoba memakai
Replit sidecar.

## PHASE 7 — SCALING AND COST REVIEW

Review konfigurasi:

automatic_scaling:
  min_instances: 1
  max_instances: 10
  target_cpu_utilization: 0.65

Untuk deployment pertama/staging verification, ubah menjadi konfigurasi hemat
biaya kecuali ada alasan terukur untuk selalu menjaga satu instance aktif.

Rekomendasi awal:

automatic_scaling:
  min_instances: 0
  max_instances: 3
  target_cpu_utilization: 0.65

Jelaskan dampak:

- cold start;
- biaya;
- database connection;
- concurrency;
- background job.

Audit apakah aplikasi menjalankan cron, scheduler, queue consumer, atau
background loop di dalam process. Jika ada, jangan mengandalkan instance web
yang dapat scale to zero untuk pekerjaan terjadwal.
