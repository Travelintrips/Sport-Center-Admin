Tolong refactor loader Google Secret Manager agar mendukung arsitektur baru:

**DEV dan PROD sekarang menggunakan satu Secret Manager secret yang sama**, bukan lagi secret terpisah berdasarkan nama.

Saat ini loader masih memakai aturan lama yang mengharuskan Secret ID mengandung marker:

* `dev` / `development`
* `prod` / `production`

Akibatnya secret generik seperti:

`sport-center`

ditolak dengan error:

`secret environment marker is missing or ambiguous`

## Tujuan

Ubah desain dari:

`environment ditentukan dari nama secret`

menjadi:

`environment ditentukan dari runtime/config eksplisit`

Lalu satu secret yang sama boleh berisi konfigurasi DEV dan PROD secara terpisah.

Contoh struktur payload yang diharapkan:

```json
{
  "dev": {
    "database_url": "...",
    "supabase_url": "...",
    "supabase_key": "..."
  },
  "prod": {
    "database_url": "...",
    "supabase_url": "...",
    "supabase_key": "..."
  }
}
```

Nama field aktual boleh mengikuti schema yang sudah dipakai aplikasi. Jangan mengubah schema lebih jauh dari yang diperlukan.

## Aturan keamanan yang wajib dipertahankan

Jangan sekadar menghapus validasi DEV/PROD.

Ganti validasi berbasis nama secret dengan validasi environment eksplisit.

Environment harus berasal dari source of truth yang sudah ada, misalnya:

`APP_ENV`

atau:

`NODE_ENV`

atau konfigurasi runtime lain yang memang sudah digunakan aplikasi.

Jika project sudah memiliki mekanisme environment sendiri, gunakan mekanisme itu dan jangan membuat duplikasi yang tidak perlu.

Mapping harus eksplisit:

`dev` / `development` → hanya section DEV

`prod` / `production` → hanya section PROD

Jika environment:

* kosong
* tidak dikenal
* ambigu

maka aplikasi harus **fail-closed**.

Jangan pernah memilih PROD sebagai default.

## Secret Manager

Tetap gunakan satu secret, misalnya:

`GCP_SECRET_ID=sport-center`

Secret ID tidak perlu lagi mengandung marker `dev` atau `prod`.

Target akses tetap:

`projects/<project-id>/secrets/<secret-id>/versions/latest`

Jangan membuat secret baru hanya karena nama secret tidak memiliki marker environment.

## Bootstrap

Pertahankan mekanisme bootstrap credential yang sudah ada.

Jangan log:

* `private_key`
* access token
* secret payload
* password database
* connection string
* seluruh bootstrap JSON

Jangan hardcode credential.

## Perubahan loader

Cari kode yang saat ini melakukan validasi seperti:

* `secretId.includes("dev")`
* `secretId.includes("development")`
* `secretId.includes("prod")`
* `secretId.includes("production")`
* `secret environment marker is missing or ambiguous`

Hapus ketergantungan environment terhadap nama Secret ID.

Ganti dengan alur:

1. Parse bootstrap/config.
2. Tentukan runtime environment secara eksplisit.
3. Validasi environment.
4. Resolve `project_id`.
5. Resolve satu `secret_id`.
6. Akses `versions/latest`.
7. Parse payload JSON.
8. Pilih section sesuai runtime environment.
9. Validasi field wajib untuk environment tersebut.
10. Return hanya konfigurasi environment tersebut.

Contoh:

```js
const env = resolveRuntimeEnvironment();

if (env !== "dev" && env !== "prod") {
  throw new Error("Unsupported runtime environment");
}

const secretPayload = await loadSecretFromGcp();

const selectedConfig =
  env === "dev"
    ? secretPayload.dev
    : secretPayload.prod;

if (!selectedConfig) {
  throw new Error(`Missing ${env} configuration in shared secret`);
}
```

Sesuaikan dengan TypeScript/style/project yang sudah ada.

## Isolasi DEV/PROD

Sangat penting:

Saat runtime DEV:

* hanya section DEV yang boleh digunakan
* jangan membaca/menggunakan config PROD
* jangan fallback ke PROD jika DEV tidak ada

Saat runtime PROD:

* hanya section PROD yang boleh digunakan
* jangan fallback ke DEV

Jika section yang sesuai tidak tersedia:

`FAIL CLOSED`

Contoh:

`DEV config missing in shared GCP secret`

atau:

`PROD config missing in shared GCP secret`

## Validasi payload

Tambahkan validasi schema secukupnya.

Untuk setiap environment, pastikan field yang dibutuhkan aplikasi tersedia sebelum API start.

Jangan print nilainya.

Log aman cukup seperti:

`Shared GCP secret access: PASS`

`Runtime environment: DEV`

`DEV configuration validation: PASS`

atau:

`DEV configuration validation: FAIL - required field missing`

Tanpa menampilkan nilai secret.

## Error handling

Pertahankan error Google asli secara sanitized.

Jangan ubah semua error menjadi:

`OTHER`

Jika Secret Manager gagal, log:

```js
console.error("Secret Manager access failed", {
  name: err?.name,
  code: err?.code,
  message: err?.message,
  details: err?.details,
});
```

Pastikan object error tidak mengandung credential atau payload.

## Compatibility

`GCP_PROJECT_ID` dan `GCP_SECRET_ID` boleh digunakan hanya jika memang desain konfigurasi saat ini menetapkannya sebagai source of truth.

Jika single-bootstrap masih menjadi source of truth utama, pertahankan itu.

Yang harus dihapus adalah **asumsi bahwa nama Secret ID menentukan environment**.

Jangan melakukan perubahan konfigurasi lain yang tidak diperlukan.

## Testing

Setelah refactor:

1. Jalankan typecheck.
2. Jalankan build.
3. Test runtime DEV.
4. Pastikan DEV dapat membaca shared secret.
5. Pastikan hanya section DEV yang digunakan.
6. Test bahwa DEV gagal jika section `dev` dihapus.
7. Test bahwa DEV tidak fallback ke `prod`.
8. Test PROD secara terpisah bila test aman tersedia.
9. Pastikan secret payload tidak muncul di log.

Expected DEV:

```text
Bootstrap parse: PASS
Runtime environment: DEV
GCP project resolution: PASS
GCP secret resolution: sport-center
Secret Manager access: PASS
Shared secret payload parse: PASS
DEV section resolution: PASS
DEV configuration validation: PASS
API startup: PASS
```

Tidak boleh lagi muncul:

`secret environment marker is missing or ambiguous`

hanya karena Secret ID bernama:

`sport-center`

## Batasan

Jangan:

* membuat secret DEV/PROD terpisah lagi
* mengganti service account
* membuat service-account key baru
* menghapus IAM
* menggunakan database fallback
* menggunakan PROD sebagai fallback DEV
* hardcode credential
* mencetak secret payload
* menonaktifkan fail-closed
* melakukan refactor besar yang tidak terkait

Lakukan perubahan sekecil mungkin.

## Laporan akhir

Setelah selesai, laporkan:

1. Root cause kode lama.
2. File yang diubah.
3. Fungsi yang diubah.
4. Bagaimana environment sekarang ditentukan.
5. Bagaimana section DEV/PROD dipilih.
6. Hasil typecheck.
7. Hasil build.
8. Hasil test DEV.
9. Konfirmasi bahwa PROD tidak digunakan sebagai fallback.
10. Konfirmasi bahwa tidak ada secret/credential yang dicetak ke log.

Jangan menyatakan selesai sampai runtime DEV berhasil melewati akses Secret Manager dan memilih section DEV dari shared secret.
