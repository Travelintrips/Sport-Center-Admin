# Payment events Google Sheets — safe rollout gate

The existing `PAID <MONTH> <YEAR>` 14-column tabs remain booking-based and must not be reused to append DP or second payments. A separate payment-event tab must use a stable `source_key` in column A, followed by source type, linked booking/member/invoice, payment timestamp WIB, actual payment amount, and reconciliation status. It must not write to Sport Center payment tables or BizPortal journal tables.

`booking_sheets_payment_sources` already projects direct, allocation, and corporate invoice line items. Membership events come from confirmed `sport_membership_payments` rows, keyed by membership payment ID (not booking ID); the read-only candidate view exposes them separately. Payment date uses `confirmed_at` until the distinction between actual payment date and confirmation date is validated. The new ledger is initially disabled and has no backend write permissions; its installation does not activate synchronization.

Before enabling: verify the actual membership payment schema and invoice paid-date semantics; test direct/DP, multiple allocations, single and repeated membership payments, corporate invoice items, cross-month transfers, duplicate webhook/confirmation, Sheets append timeout, worker crash after append, and Google Sheets reconciliation after ambiguous responses in DEV. Ensure no spreadsheet append occurs without a unique ledger claim and pre-write cross-tab duplicate scan. Apply scoped RLS only after test pass. Deploy code separately, then enable for a future `start_at`, never retroactively.
